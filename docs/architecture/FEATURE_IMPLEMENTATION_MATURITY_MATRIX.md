# Feature implementation maturity matrix

## Interpretation

The registry currently declares 8 Modules and 35 Features. `status`, `supportsWeb`, `supportsMobile`, `supportsApi`, and `supportsOffline` describe intended catalog metadata, not verified delivery. The API currently returns `registryMismatch: false` for every feature and reports `healthStatus: HEALTHY` without comparing registry claims with implementation evidence. Those values must not be used as production-readiness proof.

Maturity labels used here:

- **REAL:** persisted API and web consumer exist, with appropriate security/tenancy/tests.
- **PARTIAL:** some real model/service/API exists, but critical production layers are missing.
- **UI PROTOTYPE:** route/component exists with static or local data; no domain API authority.
- **CATALOG ONLY:** registry declaration only or only weak visual fragments.
- **NOT AUDITED:** repository is outside this audit (not a claim of completion).

No registered domain Feature is currently REAL by the definition above. The Platform Module catalog itself is real/partial infrastructure, but it is not one of the registered product Features.

## Production maturity contract

Replace the ambiguous claim with separately owned facts:

- Registry support intent: developer-owned booleans for platforms the capability is designed to support.
- Implementation evidence: build-time manifest/test evidence linking implementation key to web route, API module, mobile entry point, offline strategy, and last verification commit.
- Release readiness: operational state controlled by release governance, not inferred from a screen or model.
- Commercial availability: Module inclusion in a published PlanVersion; never Feature-level entitlement.

A Feature cannot be labeled production-ready until its tenant isolation, permission, API integration, error/loading/empty behavior, migration, and tests pass. A successful frontend build alone is insufficient.
